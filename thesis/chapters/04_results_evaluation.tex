\section{Results}
\label{cha:results}

This chapter presents the results from our two-month-long benchmark of image optimization, focusing on performance metrics collected across two serverless platforms, and 54 image optimization configurations per platform. Instead of optimized images, the image optimization functions described in Section \ref{sec:results-collection-data-analysis} return a handful of characteristics, such as the cold start flag, image processing duration, and optimization invocation time. The measurements cover a period of 62 days between December 2024 and February 2025.

\subsection{Missed Executions}
Missed execution is a situation when we expect a response from the image optimization function and a corresponding record in the database, but the number of recorded observations is smaller than expected. The benchmark does not explicitly record such situation in any way, however, any error occurrences can be reasoned about by the observation of a lower than expected number of data points for a given time frame and a set of optimization parameters. For example, when surveying the results for specific function variant over a duration of one hour, 12 data points can be expected. A lower number of measurements is a very strong indicator\footnote{Due to the distributed nature of the scheduler service, there can be a delay of several seconds between the time the scheduled rule is triggered and the time the target service runs the target resource.} of missed executions of that specific functions in the selected period of time. The benchmark does not additionally track the effectiveness of the rule scheduler itself.

From exactly $1928448$ scheduled executions in total:
\begin{itemize}
  \item workload generator collected responses from $1924484$ ($99.79\%$) executions,
  \item workload generator missed responses from $3964$ ($0.21\%$) executions,
  \item $63.94$ data points were missed on an average day. 
\end{itemize}

From $964224$ scheduled executions per provider,
\begin{itemize}
  \item benchmark collected 961113 ($99.68\%$) and missed 3111 ($0.32\%$) executions from AWS,
  \item benchmark collected 963371 ($99.91\%$) and missed 853 ($0.09\%$) executions from GCP,
  \item AWS failed to deliver responses $3.65$x times more often than GCP.
\end{itemize}

\subsection{Cold Starts}
Cold start latency is not specifically recorded as part of this benchmark. In the serverless image optimization scenario, we exclusively focus on the image optimization latency. Nevertheless, the benchmark is collecting data about an \emph{occurrence} of the cold start. This value could be inferred from the \emph{handlerCount} metric, but the optimization functions are also setting an additional property called \emph{coldStart} for convenience.

From exactly 1924484 collected responses in total:
\begin{itemize}
  \item workload generator recorded $1878363$ ($97.60\%$) warm starts,
  \item workload generator recorded $46121$ ($2.40\%$) cold starts.
\end{itemize}

From $961113$ and $963371$ of collected data points from AWS and GCP respectively,
\begin{itemize}
  \item benchmark recorded $915965$ ($95.30\%$) warm and $45148$ ($4.70\%$) cold starts on AWS,
  \item benchmark recorded $962398$ ($99.90\%$) warm and $973$ ($0.10\%$) cold starts on GCP,
  \item it was $48.18$ times more likely to observe a cold start on AWS than on GCP.  
\end{itemize}

\subsection{Measuring Image Processing Duration}
This metric determines how quickly optimized images are ready to be delivered to end users. It is measured in millisecond resolution and captures the core operation of transforming images according to specified optimization parameters. It is heavily related to the performance settings, such as amount of compute assigned to the function, output format and width, as well the input image resolution. For completeness, two visualizations of absolute optimization times are provided for one of the images in all 54 function variants.

Please note that lower performance settings imply longer processing duration. Different output formats have different computational complexity, with JPEG having the shortest processing times, and AVIF having the longest. Different providers also exhibit difference in processing duration, even for \emph{"the same"} compute (vCPUs) and memory configurations. In absolute numbers, Lambda is consistently outperforming Cloud Run functions across all output formats, output widths, and all performance setting configurations.

\subsection{Handler Count-Related Processing Duration Variability}
We have observed increased average image processing duration on the first 3 to 6 optimization invocations. This should be not confused with the \emph{cold start latency}. This is the duration of the individual image optimization instruction within the function handler.

On average, the first execution of the image optimization on AWS Lambda is around 7\% higher than baseline. Actually, it is a bit more than that, due to the relative commonness of the cold starts on this platform, and given the p100 handlerCount on AWS Lambda presented in the previous section is only 28. This effect is also noticeable, but not so pronounced on Google Cloud Run functions, where the value reaches only 3\% above the \emph{true} baseline. \subsection{Environment Variability}
The following metrics showed a mix of constant and provider-dependent variable behavior. The prime example is the Lambda function with 885 MB of memory, where we observed 5 different CPU configurations and 8 different memory configurations. While over 90\% of Lambda functions use a \emph{typical} configuration, there have been several cases when functions were granted significantly more compute or memory than requested. 
\begin{itemize}
  \item \emph{providerArch} - x64 across all function variants on both serverless platforms,
  \item \emph{providerCpus} - variable on AWS, but constant on GCP,
  \item \emph{providerMemoryAvailable} - variable on AWS, but constant on GCP, these metrics represent the actual vCPU and memory available from within the function,
  \item \emph{providerNodeVersion} - v20.18.0 across all function variants.
\end{itemize}

\subsection{Results Discussion}
We have presented 8 different categories of results detailing the performance and behavior of serverless image optimization on AWS Lambda and Google Cloud Run functions. These results span missed executions, cold starts, temporal processing variations, and underlying environment configurations. Several key differences between the platforms, and their implications for practical image optimization deployments, are worth highlighting.

The \textbf{cold start frequency} is a major difference between providers. AWS Lambda experienced cold starts in 4.7\% of invocations, almost 50 times more often than Google Cloud Run functions' 0.1\%. This may influence platforms' applicability for latency-sensitive applications. The benchmark is exploring on-demand image-optimization performance, but in the web delivery practice, images are cached on further web stack layers, and reused among multiple users. Most of the subsequent requests for images can be served from caches, but selected users who happen to be accessing a not-yet-optimized image may see a slight latency increase if the image optimizing function has not been previously used.

The contrast in \textbf{reliability, measured by missed executions}, is also immediately visible. Lambda's 0.32\% missed execution rate, compared to Google Cloud's 0.09\%, translates to a 3.5x higher failure rate. For high-volume image optimization services, this difference could mean thousands failed executions per million requests. At the same, we image processing functions have not been architected with reliability, but portability in mind. We were not collecting error traces, and failures could essentially happen at any layer of the benchmark. While both platforms exhibit a high overall success rate exceeding 99.6\%, the failure rate might necessitate more retry mechanisms or error handling in client applications, particularly those demanding high availability. This may also indicate differences in how different platforms handle functions' errors and timeouts.

Google Cloud's aggressive \textbf{environment reuse}, with maximum environment lifetime exceeding 20 days and almost 6000 requests served from the same function instance, compared to Lambda's 2 hours and 28 executions, suggest a fundamentally different approach to the environment reuse. While a \emph{warm instance} may be advantageous for the clients from the latency perspective, more predictable cold start frequency on AWS may (or not) translate to other operational benefits not directly visible for the users, such as better load balancing, or noisy neighbor avoidance.

\textbf{Variations in absolute image processing duration}, while expected given the differences in image formats, resolutions, and performance settings, also reveal provider-specific nuances. Even with comparable compute and memory configurations, difference in performance was obvious between both providers. On average, AWS Lambda was around 10\% faster given the same amount of vCPUs and memory in absolute numbers. This directly affects pricing comparison of both offerings, as 1vCPU on AWS $\neq$ 1vCPU on GCP.

The \textbf{temporal variability} observed daily, hourly, and minutely in processing durations highlights the dynamic nature of serverless platforms. The hourly fluctuations, in particular, suggest that there is an increased demand for compute around the beginning of every hour. Also, we are able to clearly see daily usage peak around 1:30pm UTC, which translates to 8.30am Eastern Time, where the benchmark was running. Secondly, the high usage period lasts until 8pm UTC, which translates to 3pm Eastern Time. If peak serverless demand overlaps with periods of increased image processing, developers might need to provision additional resources or implement more sophisticated scaling policies (such as \emph{provisioned concurrency}) to maintain consistent service levels.

Finally, the \textbf{variability in the amount of vCPUs memory} available on AWS Lambda, despite consistent configuration settings, introduces an element of unpredictability. While the majority of environments were usually given an expected memory and compute configurations, the presence of outliers suggests that the underlying hardware provisioning is not entirely uniform. It's worth noting that Google Cloud Run functions demonstrated fully consistent hardware configuration during two months of benchmarking.

Also, the \textbf{increased processing time for the initial few invocations within serverless functions}, more pronounced on AWS, suggests a \emph{warm-up} period beyond the cold start itself. This might be attributed to factors like just-in-time (JIT) compilation of code, or the internal optimizations of the image processing library, such as caching of intermediate image segments. While the effect is relatively small, it is an indication that cold starts may be influencing not only the very first invocation of serverless functions across platforms.

\section{Discussion}
\label{cha:discussion}

Studying serverless image optimization performance reveals insights relevant from different viewpoints. In this section we will discuss implications for both users and operators of such systems, but also implications of this benchmark on the wider serverless performance research.
% We will conclude by looking at the study through the perspective of cloud computing being a modern utility that is consumed in a way similar to electricity or water.

% \subsection{User vs. operator perspective}
From the user's perspective, the key insight is the nuanced performance landscape. While serverless promises on-demand scalability, the reality includes variability. This is less of a concern if images are immutable and can be cached for a long period of time, which is a common practice in web delivery. However, for scenarios where cache misses are frequent, or real-time optimization is critical, the choice of the platform (self-hosted, serverless, third-party SaaS, or other) becomes important.

Daily and weekly temporal variability in processing times, though on the order of a few percent, highlights that serverless environments are not static. In the image optimization scenario, variability is less prominent than in previous, general research on this topic. It is however measurable, and highly variable across FaaS platforms. 

From the operator's perspective, choosing a serverless platform for image optimization requires finding a balance between reduced infrastructure management and potential limitations in fine-grained control over image processing parameters. While Google Cloud Run functions offer lower number of cold starts and more consistent hardware configuration, this does not necessarily translate to more performant image handling. AWS Lambda has a more mature ecosystem and wider adoption, which might be advantageous for integration with other services, but at the same time a cold start occurrence is almost guaranteed if the function is running over two hours. Ultimately, also the location of the original images that matters - deploying compute closer to the data can reduce latency and increase throughput while downloading unoptimized images. Pricing-wise, our benchmark showed that AWS Lambda was consistently faster at image optimization when configured with the same memory and compute. To achieve comparable optimization speeds on Cloud Run, operators might need to allocate more vCPUs, which will directly impact costs.

It's worth noting that both platforms support ZIP deployments and support use of OS/CPU-specific libraries like sharp. This makes deployment simpler and lets operators leverage the performance benefits of highly optimized native libraries. Initially, it wasn't certain whether both platforms would such straightforward support. In our opinion, this will be a contributing factor to the success of efficient serverless functions across both AWS Lambda and Google Cloud Run functions.

In terms of wider serverless performance research, we have expected (and eventually confirmed) a smaller performance variability comparing to strongly CPU- or IO-bound benchmarks. We were surprised to discover that Google Cloud Run functions were able to keep the state for over 20 days, which may have been an exception, nevertheless does not seem to be common experience in the serverless community. We also did not expect \emph{that} predictable cold start behavior on AWS Lambda - our benchmark showed that there was very little, almost no randomness to when a function starts cold. This however may be only applicable to ZIP deployments like in our benchmark, and not directly translatable to container-based workloads.
